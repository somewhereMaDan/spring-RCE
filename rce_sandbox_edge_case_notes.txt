RCE SANDBOX — EDGE-CASE TEST NOTES

Purpose

Record the security tests run against the Python execution container,
what each test demonstrated, and which Docker setting provides the
protection.

TEST RESULTS

1.  Non-root execution and privilege restrictions — PASSED 
    Test: Read
    /proc/self/status. Observed: Uid: 1000 1000 1000 1000 CapBnd:
    0000000000000000 NoNewPrivs: 1 
    
    Why it passes: The process runs as UID 1000, has an empty capability bounding set, and has
    no_new_privileges enabled. Relevant options: –cap-drop ALL –security-opt no-new-privileges

2.  Root filesystem write protection — 
    
    CONFIGURATION VERIFIED 
    Observed with docker inspect: ReadonlyRootfs = true 
    
    Why it matters: The container’s root filesystem is mounted read-only. Writable locations
    must be explicitly provided. Relevant option: –read-only

3.  Temporary-file disk exhaustion — PASSED 
    
    Test: Write 1 MB repeatedly
    to /tmp, up to 1 GB. Observed: stopped 32 [Errno 28] No space left
    on device wrote 32 MB Why it passes: /tmp is a separate tmpfs with a
    32 MB size limit. 
    The write fails when that filesystem reaches its
    limit, rather than growing the container’s writable root layer.
    Relevant option: –tmpfs /tmp:rw,noexec,nosuid,size=32m

4.  Fork bomb / process creation — TIMEOUT OBSERVED; 
    PID LIMIT CONFIG VERIFIED 
    
    Test: Repeatedly call os.fork(). 
    Observed: Verdict = TLE
    Exit code = 137 
    
    Docker inspection confirmed: PidsLimit = 128 Why it
    is protected: The PID cgroup limit caps the number of processes the
    container can create. 
    The execution timeout then terminates the runaway job. 
    Relevant protections: –pids-limit=128 Application
    wall-clock timeout.
    
    Note: The TLE result alone does not prove the PID
    limit caused termination; the Docker inspection confirms that the
    limit was applied.

5.  Infinite CPU loop — PASSED 
    
    Test: while True: pass 
    Observed: Verdict = TLE Exit code = 137 Wall time approximately 10 seconds 
    
    Why it passes: The application timeout terminates code that does not
    finish. CPU quota also limits the container’s CPU share. Relevant
    protections: –cpus=0.25 Application wall-clock timeout

6.  Network access — PASSED 
    Test: Attempt TCP connection to 1.1.1.1:80.
    
    Observed: OSError [Errno 101] Network is unreachable. 
    Why it passes: The container has no network interface with external connectivity.
    Relevant option: –network none

7.  Memory exhaustion — MLE OBSERVED 
    Test: Repeatedly allocate and retain 1 MB strings. Observed: Verdict = MLE Exit code = 137 Wall time approximately 750 ms 
    
    Why it is consistent with the limit: The process was terminated while allocating memory, consistent with the
    container reaching its configured memory limit. 
    
    Relevant options: –memory=128m –memory-swap=128m Note: Exit code 137 alone does not
    prove an OOM kill. For stronger confirmation, inspect Docker’s
    OOMKilled field or cgroup memory events for a retained test
    container.

SANDBOX SETTINGS VERIFIED

–memory=128m –memory-swap=128m –cpus=0.25 –network none –pids-limit=128
–read-only –tmpfs /tmp:rw,noexec,nosuid,size=32m –cap-drop ALL
–security-opt no-new-privileges

WHY THESE TESTS PASS NOW

The Docker run command now applies resource limits and isolation
controls to the execution container. In particular:

-   –read-only prevents writes to the container root filesystem.
-   A size-limited tmpfs gives /tmp a bounded writable area.
-   Memory, CPU, and PID cgroups constrain resource consumption.
-   –network none removes external network connectivity.
-   Dropped capabilities and no-new-privileges reduce privilege
    escalation.
-   The application’s wall-clock timeout stops jobs that run
    indefinitely.

IMPORTANT NOTES

-   A per-container memory limit does not cap total memory across all
    jobs. Worker concurrency and queue limits must protect the host
    aggregate.
-   Exit code 137 means SIGKILL; it does not by itself identify the
    cause.
-   A successful test demonstrates the tested behavior, not a complete
    security audit of the sandbox.
